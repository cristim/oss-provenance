# Evidence collection

`evidence::collect` downloads public GitHub or GitLab.com evidence for a scanner candidate. It requires a repository URL, upstream path, version or commit, and upstream file MD5. It resolves the version through the host API, pins a full commit, requires complete tree responses, and verifies downloaded source against the scanner's MD5. GitLab nested namespaces are supported. SHA-256 binds retained artifacts for subsequent review. MD5 verifies the scanner's historical identity; it is not treated as a cryptographic trust anchor.

The collector retains the complete source, including its headers, root and ancestor LICENSE/LICENCE/COPYING/NOTICE/COPYRIGHT/AUTHORS files, source `.license` sidecars, and root `LICENSES/` files. These are review candidates: their location does not establish applicability. Nested exceptions and project use context still need review. A file's explicit SPDX identifier can populate a proposal, but cannot approve it. Scanner license labels are never used as permission.

Every proposal remains pending. Review the full grant text, copyright notices, exceptions and obligations, choose a concrete branch for alternative licensing, and admit the decision separately into trusted policy. The collector neither stages files nor changes policy. When no supported source license declaration exists, artifacts and issues are still returned, with no evidence decision.

Evidence must explicitly declare supported obligations: `artifact_only`, or `source_prefix` with the exact required leading `text` for every file using that source. Source prefixes can contain copyright headers and modification notices. They are checked on all active recorded uses, including deletion-only changes. Collected evidence starts with `unsupported` and a pending-review reason; it cannot clear a match. The reviewer must determine that the configured checks cover the applicable obligations. More complex obligations cannot be silently represented as folder attribution alone.

`evidence::verify_source` re-downloads an admitted source at its full GitHub or GitLab commit and checks both its MD5 and SHA-256 against trusted evidence. It returns the verified source bytes for local/upstream range comparison. Scanner-provided identity labels alone cannot establish that a local match belongs to this source.

Snippet correspondence compares exact bytes, including whitespace, operators, case and string contents. Modified snippets require separately admitted `[[reviewed_snippets]]` policy entries containing the existing `evidence_id`, `local_sha256`, `upstream_sha256`, and a nonempty `review`. Hash each complete paired line range exactly as stored, including its line endings. Every pair must either match exactly or have its own reviewed hash pair. The policy supports at most 256 mappings. Empty ranges, invalid boundaries and whitespace-only ranges remain unsupported; full-file matches must remain byte-identical.

Mappings live at the policy level and do not change evidence IDs or existing notices. Admit them through the ordinary immutable policy-reference workflow after reviewing the exact modification and grant applicability. An admitted mapping still requires the source hashes, license rules, grant artifacts, obligations and reuse notices to pass. A later edit to either range requires a new review; scanner similarity scores cannot admit modifications.

Downloads use only `api.github.com`, `raw.githubusercontent.com` and `gitlab.com`, HTTPS, no redirects, a total deadline of 1 to 300 seconds, 8 MiB per response, 32 MiB total, and at most 64 upstream files. GitLab trees require sequential page headers and terminate within 100 pages of at most 100 entries each. Requests are built locally at the resolved revision; response URLs are never followed. Missing or unsupported candidate metadata and source-hash mismatches produce unresolved issues. Network, HTTP, malformed API responses, incomplete trees and resource-limit failures return operational errors. Private repository credentials, self-hosted GitLab and Bitbucket are not supported.

`collect_with_scancode_report` optionally accepts a ScanCode JSON report and an explicitly pinned expected version. The parser requires every collected file once, matching paths and MD5 values, no per-file scan errors, and the pinned tool name/version. It consumes the documented `detected_license_expression_spdx` field, rejects custom LicenseRef expressions, retains the original report, and keeps the resulting proposal pending. See the [official ScanCode output contract](https://scancode-toolkit.readthedocs.io/en/stable/reference/scancode-cli/cli-output-format-options.html).

`collect_with_scancode_executable` runs a separately installed scanner at an explicit absolute trusted executable path. It copies only the verified collected files into a private directory, with no archive extraction or candidate scripts. The process receives an empty inherited environment, private home and temporary directories, a fixed system PATH, and fixed `--license --info --strip-root --processes 0 --quiet --no-check-version --json -` arguments. Its deadline is 300 seconds and its combined stdout/stderr limit is 8 MiB. Nonzero exit, timeout, excess output, invalid version, missing files, hash mismatch, or scan errors fail collection. The returned report uses the same strict parser and remains a proposal. The library does not install tools or admit policy.

The verified tool environment uses [ScanCode Toolkit 32.4.1](https://pypi.org/project/scancode-toolkit/32.4.1/), Python 3.12.14, and Click 8.2.1. Click 8.5.0 caused this ScanCode release to reject its strip-root options in the observed environment. On macOS ARM64, installation also required ICU and libmagic. Keep the tool environment separate from the repository; the executable is trusted operator code. The caller must reject executable paths inside the candidate repository or its Git common directory. Run the actual consumer explicitly with `SCANCODE_EXECUTABLE=/absolute/path/to/scancode cargo test --test evidence live_scancode_collects_public_reference_as_pending_proposal -- --ignored`.

The CLI enforces those executable boundaries, including when invoked from a repository subdirectory or linked worktree:

```sh
oss-provenance collect-evidence --report findings.json --finding 0 \
  --scancode-executable /absolute/path/to/scancode --scancode-version 32.4.1 \
  --output /path/to/new-evidence-directory
```

Use `--scancode-report /path/to/report.json` instead to import an existing report. Both modes require `--scancode-version`; they cannot be combined. Without either ScanCode input, ordinary collection still works. A successful collection exits 1 because its saved proposal is pending review. Exercise the CLI with `SCANCODE_EXECUTABLE=/absolute/path/to/scancode cargo test --test evidence live_cli_scancode_writes_a_pending_proposal -- --ignored`.

Run the public-reference download test explicitly with `cargo test --test evidence live_public_reference_collects_actual_grant_bytes -- --ignored`. Ordinary tests do not use the network.
