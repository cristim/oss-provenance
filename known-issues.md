# Known limitations

- Automatic generation supports Claude through Docker. Codex supports manual handoffs only. Real Docker fixtures and Linux Claude fake-API tests verify isolation, attempt accounting, and recovery; successful authenticated generation through the production container remains a separate pending verification. The supplied provider Dockerfile pins an ARM64 image. Other provider architectures, Windows, and native host execution are not verified.
- Independent requirements, tests, and images require operator review. The image must supply GNU timeout and a valid executable, interpreter, and runtime. After successful executable preflight and confirmed container start, a nonzero test exit counts as a failed attempt, including runtime dependency problems. An abruptly killed resolver can leave stopped container metadata; it does not prune containers without its own ownership record.
- Application is index-only. Working-tree files can differ from the newly staged result. Automatic repair replaces entire configured files and accepts at most 128 KiB of generated contents in total; requirements and tests must cover the complete behavior to retain. Split or sparse indexes, merge conflicts, intent-to-add, assume-unchanged, skip-worktree, symlinks, and submodules are unsupported for automatic application. Installed conflicts require manual review; terminal recovery does not run a new provenance check.
- New source evidence and modified-snippet mappings require human admission. Public GitHub and GitLab.com are supported; private repositories, self-hosted GitLab, and other source hosts are not. ScanCode can run from a separately installed trusted executable, but its reports do not establish grant applicability. Unresolvable versions, modified grants, custom SPDX references, ambiguous provenance, and unsupported correspondence remain unresolved.
- Caching is opt-in. Scanner responses expire after one hour; immutable source bytes are hash-checked on reuse. Mutable cached negative results require trusted storage and may miss corpus changes within that hour. Limits apply to recognized regular records in a dedicated trusted directory; unrelated files are preserved and do not count toward cache capacity.
- Processes sharing a trusted state directory coordinate requests per endpoint and persist cooldowns. Separate state directories or different endpoint URLs do not share limits. Outages can still block commits when there is no valid cache entry. Structured runtime errors distinguish scanner failures from other operational problems, but do not decide whether or when an outer agent loop should retry.
- Policy evaluation never admits a grant or clears a commit. Trusted CI pins and policy promotion remain administrator decisions. Required status names alone cannot prevent another Actions workflow from forging a check; automatic enforcement needs an authoritative required-workflow ruleset or a separate GitHub App identity. The shipped verifier checks the actual trusted run before a merge.
- There is no coverage-threshold gate. Dependency advisory and yank checks, offline tests, format, Clippy, and build checks are provided. Linux release binaries inherit the runner's glibc baseline; macOS archives are unsigned and not notarized.
